# Deep research: разделение секрета (Shamir) и MPC между роботами (2026-09-11)

## Рамка
Задача: понять механику Shamir Secret Sharing и её встраивание в secure aggregation для
флота роботов — какой протокол это фактически реализует, какие у него failure mode
(отвалившийся робот) и byzantine-режимы (испорченный робот), чтобы корректно
специфицировать MPC-слой privacy-проекта (было заявлено на исходном слайде как готовая
контрибуция — нужно подтвердить/опровергнуть новизну).

## Что уже известно лаборатории
Outline недоступен — не опрошено.

## Состояние области
- **Каноничный протокол secure aggregation** — Bonawitz et al., *Practical Secure
  Aggregation for Privacy-Preserving Machine Learning*, ACM CCS 2017
  (DOI 10.1145/3133956.3133982). Каждый клиент маскирует свой вклад попарными
  псевдослучайными масками (сгенерированными через общий ключ с каждым другим клиентом);
  маски взаимно уничтожаются при суммировании, сервер видит только сумму. Если клиент
  отваливается посреди протокола — его маску нужно восстановить, чтобы не испортить
  сумму: для этого доли ключей/масок каждого клиента заранее разложены схемой
  **Shamir (t, n) secret sharing** среди остальных клиентов, и при потере клиента
  оставшиеся (если их ≥ t) совместно реконструируют недостающую часть. Это стандарт,
  на котором строится Google Secure Aggregation — то есть связка «MPC + Shamir» из
  исходной колоды проекта не новый метод, а прямое применение протокола 2017 года.
- **Post-quantum вариант** — *PQSF: post-quantum secure privacy-preserving federated
  learning*, [Sci Rep 2024, DOI 10.1038/s41598-024-74377-6] — то же назначение, но
  маскирование строится на решёточной криптографии вместо DH-ключей; релевантно, если
  проект claim'ит долгосрочную устойчивость защиты.
- **Верифицируемая secure aggregation** — *Group verifiable secure aggregate federated
  learning based on secret sharing*, [Sci Rep 2025, PMC11926380]. Добавляет
  верифицируемость: группа клиентов может доказать корректность агрегации без раскрытия
  вкладов — полезно для сценария «недоверенный агрегатор», а не только
  «honest-but-curious».
- **Устранение попарной коммуникации** — гибрид Shamir SS + 2-из-2 аддитивного secret
  sharing через PRF позволяет убрать прямую связь между клиентами и пересылку через
  сервер напрямую (см. обзор *SoK: Secure Aggregation based on cryptographic schemes for
  Federated Learning*, EURECOM). Важно для флота роботов: не все пары роботов физически
  могут связаться друг с другом (разные дома), поэтому вся коммуникация всё равно идёт
  через сервер как relay, даже в «peer-to-peer»-варианте маскирования.
- **Byzantine-робастность** — *SABLE: Secure And Byzantine robust LEarning*,
  [arXiv:2309.05395]. Secure aggregation (Bonawitz-стиль) защищает от подглядывания
  сервером, но НЕ от испорченных клиентов, которые честно шлют маскированные, но
  вредоносные обновления — для этого нужен отдельный слой (робастная агрегация,
  см. отчёт по теме 4). Явный gap: в исходной колоде проекта byzantine-угроза не
  покрыта вообще.
- **Secure aggregation с ненадёжным сервером** — *Secure Aggregation with an Oblivious
  Server*, [arXiv:2307.13474] — вариант, где даже сам сервер не обязан быть
  полу-доверенным; релевантно, если threat model проекта ужесточается до «сервер тоже
  атакующий».

## Лидерборды / SOTA
Не применимо (криптографический протокол, не задача с метрикой качества); сравнение
идёт по коммуникационной/вычислительной сложности раунда — Bonawitz et al. заявляют
O(n log n) коммуникации на клиента при n участниках, что и стало стандартом сравнения
в последующих работах.

## Референс-репозитории
Прямых репозиториев не найдено в этой волне поиска — большинство реализаций secure
aggregation встроены в FL-фреймворки (см. Flower, [arXiv:2205.06117], отчёт по теме 1).

## Соседние области и перенос
- **Блокчейн / distributed ledger** → threshold-подписи на базе той же Shamir-математики;
  перенос дешёвый на уровне примитива, но добавляет consensus-overhead, избыточный для
  звёздной топологии сервер-роботы.
- **Многосторонние вычисления в финтехе (PSI, приватный аукцион)** → те же t-of-n схемы
  разделения секрета; перенос концептуальный, не даёт нового приёма для робо-специфики.

## Очередь идей (по цене проверки)
1. Явно процитировать Bonawitz 2017 как базу MPC-слоя вместо заявления «наш вклад» —
   нулевая цена, снимает риск обвинения в переоткрытии на защите/рецензии.
2. Добавить byzantine-угрозу в threat model и оценить, ломает ли испорченный робот
   глобальный квантиль/агрегат даже при честной secure aggregation ([arXiv:2309.05395]
   как отправная точка) — средняя цена, расширяет вклад C2 (почему утекает / почему
   защита неполна) на новую ось.

## Открытые вопросы
- Нужна ли verifiability (PMC11926380) в бытовом сценарии, где сервер — доверенный
  вендор (Arenadata-подобная компания), или honest-but-curious достаточно?
- Порог t в t-of-n для флота из N домашних роботов — как выбирается на практике при
  нестабильной связи (роботы часто офлайн не по злому умыслу, а по Wi-Fi)?
