# Deep Research

Широкая разведка перед тем, как браться за доменную задачу. Цель — карта области,
а не решение: что уже пробовали, чем мерили, где узкие места, какие соседние
области дают перенос.

## Когда

- Новая доменная задача / соревнование, нужно понять состояние области.
- Перед выбором подхода: собрать веер вариантов и цену их проверки.
- Пользователь просит обзор, «что уже есть», список идей.

## Инструменты этого стека

| Источник | Чем брать | Что оттуда |
|---|---|---|
| arXiv | MCP `arxiv` (`search_papers` → `get_abstract` → `download_paper`/`read_paper`, `citation_graph`) | точные версии работ, методы, метрики, заявленные ограничения |
| Веб / доки / бенчмарки | `WebSearch`, `WebFetch` | обзоры, лидерборды, репозитории, блог-посты, документация |
| GitHub | `WebSearch` + `WebFetch` (raw README) | референс-реализации, размеры моделей, лицензии |
| Внутренняя память лаборатории | MCP `outline` | прошлые гипотезы, отрицательные результаты, статусы |
| Оформленные артефакты | MCP `gdrive` | внутренние отчёты, таблицы, черновики |

## Процедура

1. **Рамка.** Из запроса вытащи: задачу, домен, известные бэйзлайны, ограничения
   (память/время/данные), критерий успеха. Если чего-то не хватает и это меняет
   направление поиска — спроси одним вопросом, иначе не тормози.
2. **Внутри до внешнего.** Сначала `outline` (и `gdrive`, если есть) — не решала ли
   лаборатория это или соседнее. Зафиксируй, что уже известно и что не сработало.
3. **arXiv.** 2–4 запроса разной широты. Для 5–15 самых релевантных — карточка:
   `автор/год · метод · датасет · метрика · ограничение · arXiv id/версия`.
   Ключевые статьи скачивай (`download_paper`) и читай разделы про метод и метрики.
4. **Веб и код.** Лидерборды, SOTA-таблицы, обзоры, референс-репозитории. Для репо —
   READ raw README: размер модели, лицензия, воспроизводимость.
5. **Соседние области.** Явно найди 2–3 области, где эта же проблемная часть уже
   решена, и оцени стоимость переноса приёма.
6. **Синтез.** Отчёт по шаблону ниже. Каждый факт — со ссылкой. Идеи упорядочены
   **не по ожидаемому качеству, а по цене проверки и воспроизводимости**.
7. **Сохранение.** Запиши отчёт в `research/<slug>-<YYYY-MM-DD>.md`. Спроси, залить
   ли его в Outline (база идей) — не заливай без подтверждения.

## Шаблон отчёта

```markdown
# Deep research: <задача> (<дата>)

## Рамка
задача · домен · бэйзлайны · ограничения · критерий успеха

## Что уже известно лаборатории
- ... (Outline/Drive ссылки) — включая отрицательные результаты

## Состояние области
- <метод> — <кто/год> — <метрика на датасете> — <ограничение> — [arXiv:xxxx.xxxxx v2]

## Лидерборды / SOTA
| подход | метрика | железо/бюджет | ссылка |

## Референс-репозитории
- repo — размер модели — лицензия — воспроизводимость — url

## Соседние области и перенос
- область → приём → стоимость переноса → риск

## Очередь идей (по цене проверки)
1. <идея> — минимальный эксперимент — что подтвердит/опровергнет — цена
2. ...

## Открытые вопросы
```

## Правила

- Ни одного факта без ссылки. Версия работы фиксируется (arXiv id + v).
- Отрицательные результаты — такой же выход, как положительные, не выкидывай.
- Не смешивай разведку и решение: тут только карта области и очередь идей.
- Если запускаешь параллельные под-разведки (несколько под-тем) — своди в один отчёт,
  не дублируй уже найденное.
